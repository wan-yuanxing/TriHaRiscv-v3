# Video 适配既有 YuNet 320 输入

## 决策与依据

用户在外部NPU交接审查be3fccc后选择：实现难度可控时，优先迎合NPU现有设计。后续检测输入目标采用外部提交4fc0fc8的320×320、UINT8 BGR NCHW方案。其原始ONNX为640×640，320×320是对方已派生、校准和评价的版本；复用的依据是该已验证版本。

本决定替代v0.6中检测输入160×128/5×5块平均/C8作为后续集成目标的选择，历史组件及验收记录保持原范围。HDMI仍为800×600、约60.32Hz，显示仍为800×600双400×300预览，不采用外部文档的720p/30fps视频建议。

比较过三条路线：保留160需要NPU重新派生/校准/评价；把160插值放大至320不能保持现有模型预处理；直接从800×600执行既有320处理可复用模型基线，采用第三条。

## 固定尺寸预处理

RGB888 800×600 → BGR UINT8双线性320×240 → 上下各补40行raw零 → B/G/R紧密三平面320×320。编码为0..255、scale=1、zero-point=0，无 `/255`、signed重解释或额外有损输入量化。每行320B、每平面102400B、共307200B。B/G/R平面偏移0/0x19000/0x32000。

采用OpenCV4.11.0的INTER_LINEAR语义。目标有效坐标x/y的源起点为 `floor((10*d+3)/4)`，右/下权重在偶坐标为3、奇坐标为1，权重分母4。对单通道：

```text
H0 = (4-wx)*p00 + wx*p01
H1 = (4-wx)*p10 + wx*p11
q  = (floor((4-wy)*H0/4) + floor(wy*H1/4) + 2) // 4
```

必须保留分步取整；直接 `(完整加权和+8)//16` 并不等价。已通过隔离加载的官方4.11.0.86 Windows wheel核对全部1021²种水平和组合及四种相位，共4169764例，优化开/关均一致；普通单次舍入在390152例不同。六幅完整RGB源图的NCHW哈希也已冻结。该证明只覆盖固定800×600→320×240，不能扩展为通用缩放器结论。

## 分批实现边界

第一批冻结不依赖OpenCV的逐像素整数参考及golden来源，使后续RTL有独立oracle。本轮实施计划只覆盖这一可独立验收的数值基础。

后续RTL使用固定5输入列→2输出列、5输入行→2输出行相位：取列/行0、1与3、4进行插值，第2项只参与输入几何检查。可在前一有效源行保存320个三通道10bit水平和，共9600bit逻辑存储，用移位加法实现1/3系数。同步行RAM、流水和背压需要定向验证及PDS后才能确认资源/125MHz时序，当前不作综合或连续采集保证。

NCHW写入采用有界行缓存和显式地址描述符：逐行收集B/G/R，再分别写到对应平面的行地址，可复用既有128bit单平面DMA。三个平面和已有raw/preview之间按事务仲裁；所有分支写响应和good EOF齐备后才发布正式完成。fault不撤销已公开VALID，取消后排空已公开事务，旧frame_id不能污染新任务。三分支及板测另作实施批次。

300KiB输入超过旧256KiB槽。建议在现有1MiB输入区按320KiB/槽分配：候选A/B/C为0x82800000/0x82850000/0x828A0000，末64KiB保留；每槽实际张量300KiB。该候选须写入唯一公共地址配置并与CPU联调，不能将文档候选当作已实现译码。已验收板级目标目前继续使用原配置，公共生成定义在新入口接入时统一迁移，禁止分别手改RTL/C宏。

## 验收顺序

1. Python整数参考与六幅OpenCV4.11 golden逐字节身份一致，非法长度/类型被拒绝。
2. 固定比例RTL逐像素匹配参考，覆盖四相位、0/255/取整边界、长背压、行末错误、未知值和clear/reset；组件综合保持8ns约束。
3. NCHW/DMA字节内存联测覆盖平面边界、padding、stride、4KiB拆分、末写响应暂停、错误与取消；同步迁移公共配置/地址。
4. 三分支同帧、共享fabric/可见性、帧槽所有权和真实HDMI板测分别验收。用户确认的320目标不等于这些集成已完成，也不复用320软件AP作为板测成绩。
