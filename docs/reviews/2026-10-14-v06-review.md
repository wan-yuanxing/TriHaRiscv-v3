## 1. 发现的问题

### F1 · P2：调度伪代码把单算子空闲当成整图空闲

原始位置：修订前第 587–588 行（第 9.5 节）。关联修订前第 397、398、701、711–723 行。当前见[规格第 9.5 节](D:/FPGA/TriHaRiscv-main/docs/TriHaRiscv_SoC_Design_Spec_v0.6.md#95-建议的事件驱动调度)。

NPU 的 IDLE/BUSY 只覆盖当前算子，而第 587 行以“NPU 空闲且有 READY 槽”启动一帧算子表。三帧槽重叠时，A 帧算子 k 已 DONE、算子 k+1 尚未 START，B 帧又已 READY；若按建议事件循环顺序执行，可能先启动 B，再继续 A。两帧将争用同一 NPU 和共享中间张量区。

全文已有“一个推理任务”的上层约束，因此这不是缺少单帧原则，而是建议调度条件不足以落实该原则。最小修订：

```text
若无活跃整图任务（graph_active=0）、NPU IDLE 且有 READY 槽：
    锁定 frame_owner 和模型工作区，开始该帧算子表
若当前算子 DONE 且仍有后续算子：
    只继续 frame_owner 对应的下一算子，不重新选择 READY 槽
若最后算子输出写完成且共享中间工作区不再被本帧消费者使用：
    释放整图计算所有权，允许选择下一帧
```

不必等待该帧显示结束才释放计算引擎。若允许 CPU 处理上一帧检测头时 NPU 开始下一帧，需证明输出分槽、CPU 工作区和中间张量生命周期互不冲突。

验收向量：A 最后几个算子之间随机插入 CPU 延迟，B 提前 READY；断言 A 全图结束前不会接受 B 的算子，输出和 frame_id 均与各自整数参考一致。

### F2 · P2：完整处理时间和可见延迟的分解漏了等待调度

原始位置：修订前第 879–884 行（第 13.3 节）。关联修订前第 851、567、587、925 行。当前见[规格第 13.3 节](D:/FPGA/TriHaRiscv-main/docs/TriHaRiscv_SoC_Design_Spec_v0.6.md#133-逐帧时间轴)。

第 851 行把完整处理时间定义为 `INPUT_READY → RESULT_READY`，第 879 行却只相加 NPU、后处理和头像命令时间。三槽重叠时，输入准备好后等待上一帧释放 NPU 的时间可能显著大于零。

可复现场景：A 正在显示，B 在 t=0–40 ms 推理，C 在 t=16 ms 已经输入就绪。C 等到 t=40 ms 才运行，之后执行 40 ms。忽略后处理时，C 的完整处理时间为 64 ms，原分解式只有 40 ms，随后可见延迟公式也少算 24 ms。

建议用以下事件区间定义，保持实际事件差为最终依据：

```text
T_wait_dispatch = DET_START - INPUT_READY
T_service       = RESULT_READY - DET_START
T_process       = T_wait_dispatch + T_service

T_visible = (INPUT_READY - FRAME_SOF)
          + T_process
          + (DISPLAY_COMMIT - RESULT_READY)
          + (SHOW_LEFT_FIRST - DISPLAY_COMMIT)
```

其中 `T_service` 再细分 NPU 图执行、CPU 后处理、头像命令及其他实际调度开销。接口冻结时同时明确 `INPUT_READY` 与三分支 `CAPTURE_DONE` 的关系，避免神经网络输入先写完、原图/preview 尚未完成时遗漏额外等待。

### R2：明确 CPU 导入来源及不兼容项

规格第 244–261 行已经描述 IF1/IF2/ID/EX/MEM/WB 六级和 32-bit 取指，不要求恢复五级板测前置。可按该路线继续开发。

但是，工作区另一个工程正在做 CVA6 单发射交付候选。若 CPU 线准备导入它，需要先记录与规格的差异，而不是把“六级单发射”作为全部兼容性依据：

- 流水阶段/scoreboard、CPU 对外统一 AXI 与规格第 604 行的 32-bit 指令/数据接口并不相同。
- 候选采用的 Cache 行宽、写策略和缓冲不能自动等同于第 269–273 行的 32B、WT/NWA、等待写响应后完成 store。
- [最新单发射状态记录](D:/FPGA/TriHaRiscv-v3-cpu-dualissue/docs/cpu/single_issue_delivery_status_2026-10-14.md)中，定向测试实际出现 `commit62 → AW65/W66/B67`，SLVERR/DECERR 未产生 trap；它仍把此项列为精确 store 缺口。FENCE.I 新候选已有定向修复记录，但不能据此推断 store 错误路径也已修复。

因此要么按规格演进原 TriHa 核，要么在导入清单中给 CVA6 适配设明确准入条件并修订不一致的接口描述。不能为了导入方便静默降低精确异常要求。本次未重新执行候选 CPU 测试，以上状态以读取时的记录为依据。

### R3：冻结 CPU–Video 的 DDR wrapper 完成语义

关联规格第 210–212、554–556、607–610、723 行。

规格要求“所有输出写响应成功后 DONE”，作为 AXI 层约定是合理的；但已有厂商 HMIC_S 接口没有标准 AXI B 响应，也没有 RREADY/WVALID。来源见 [DDR 契约第 38–46 行](D:/FPGA/TriHaRiscv-v3/targets/pango676/ddr/README.md:38)。旧桥在最后 native 写数据被接受后进入 BRESP，见 [axi128_hmic256.sv 第 154–165 行](D:/FPGA/TriHaRiscv-v3/targets/pango676/ddr/axi128_hmic256.sv:154)。

这并不自动说明旧桥错误，但总工程需要明确：

- `ddr_wrapper` 向 CPU/NPU/Video 提供哪一种标准接口，native 特殊握手由谁封装。
- B 成功代表控制器接受、可被后继读取观察到，还是其他有厂商依据的完成点。
- 跨主端 RAW 顺序由哪个模块保证，何时可以发出 CAPTURE_DONE/NPU_DONE。
- 哪些错误可由桥/控制器检测；不能把本地生成的 OKAY 解释为物理 DDR 数据错误已被全面检测。
- DDR 未就绪/失锁时的接纳、故障、排空和复位策略。

建议 Video 主责交付隐藏 native 差异的板级 DDR 封装与约束，CPU 主责发布 fabric 使用契约，NPU/Video DMA 用共同的完成/错误测试接入。至少覆盖最后写拍长等待、随后同址读、另一主端读取、复位中断事务和非法地址。

### R4：将接口草案变成三线可共用的最小契约

第 218、727、1047–1053 行已明确需要冻结，这不是文档遗漏，但正式并行联调前要实际交付。建议先做以下少量权威文件，而非立即写全套实现：

| 交付 | 主责 | 最低内容 |
|---|---|---|
| `config/soc_map` | CPU | 基址、窗口大小、cache/execute/device 属性、禁用/非法地址响应 |

| `config/video_regs`、`video_cfg` | Video，CPU 审核 | 请求接受/显示提交/旧槽释放分别 ACK；槽号、frame_id、提交记录生命周期 |
| `model/yunet/model_manifest` | NPU | 固定 ONNX/hash、形状、量化、物理布局、12 个输出张量顺序与 Sigmoid 归属 |

## 3. 已核对且未发现矛盾的部分

- 固定 HDMI 模式为 **800×600、40 MHz、1056×628**，扫描率约 60.3165 Hz；两个 400×300 窗口保持 4:3，位置和 3.96 ms 扫描偏移一致。
- 5×5 检测缩小覆盖全部输入；160×120 底部补 8 行成为 160×128。5×5 和 2×2 的舍入、Alpha 极值/非预乘规则明确。
- 每槽原图 1,440,000 B，preview 从 0x160000 起占 360,000 B，结束偏移 1,801,792 B，低于 2 MiB 且无重叠。
- 输入 163,840 B，小于每槽 256 KiB；按四组 C8 输出推导 33,600 B，小于 64 KiB 输出槽。DDR 分区相邻、不重叠，合计 96 MiB 共享区。
- YuNet stride 8/16/32 对应 320+80+20=420 位置；cls/obj/bbox/kps 共 16 个逻辑值，`sqrt(cls×obj)` 与 OpenCV 参考一致。文档已明确 logits/Sigmoid 边界需要导出验证。
- 24 fps 仅为优化目标，功能演示不以达到它为前提；不同 frame_id 的实际可见更新计数、无脸有效帧和丢弃帧的统计区分合理。
- 名义 f_cap=24、f_scan=60 时基础带宽 68.73216 MB/s 正确；已明确排除 NPU/CPU/头像流量，并要求测最坏等待而非仅看平均值。
- 三槽不是吞吐保证。READY/显示提交/RETIRING/ACK、跨域和丢整帧规则已覆盖基本正确性要求；不需要为“24不能整除60”更改固定 HDMI 模式。

未把模型导出、量化精度、DW 映射、资源和板测尚未完成列作实现 bug；规格已经将它们列为阶段 0/后续验收事项。也不能依据此审阅签署 ≥24 fps、P95≤50 ms 或整机资源/时序已经达成。

特别应优先验证真实拍摄距离下的人脸尺寸。官方 YuNet 说明检测脸尺度约从 10×10 像素起；5 倍缩小后原图约 50×50 的人脸已接近该量级。此换算只是选取验证样本的依据，不是硬性可检出阈值或精度保证。
