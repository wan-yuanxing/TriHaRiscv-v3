# P0-1/P0-2 代码修正与回归片段

日期：2026-11-03（Asia/Shanghai；运行目录时间戳为 UTC）。本片段供父任务引用，不替代最终审核报告。修改范围仅为两树 CSR/LSU 局部、当前构建清单、CSR/cache 仿真入口和相关固件；未改 LaTeX、图、issue RTL 或其他 CPU 数据通路。

## 结论与正文口径

**P0-1 已修正。** 当前维护实现使用机器模式自定义 CSR `0x7C1`（flush）、`0x7C2`（writeback）、`0x7C3`（invalidate）。`0x7C0` 的内部 timer compare 保持不变；`0x3A0–0x3A2` 不再触发维护，也不保留别名。PMP 未实现，这三个旧地址的访问进入非法指令异常。官方地址分配中 `0x7C0–0x7FF` 属于机器模式自定义读写区。

| 指令形式 | 新维护 CSR 的读值 | 维护副作用 |
| --- | --- | --- |
| CSRRW（含汇编伪指令 `csrw`） | 0 | 发起对应维护，rs1 值沿原 LSU 地址路径传递 |
| CSRRS、CSRRC | 0 | 不发起维护，不保存写值 |
| CSRRWI、CSRRSI、CSRRCI | 0 | 不发起维护，不保存写值 |

操作形式沿用原设计：只有寄存器 CSRRW 触发维护。LSU 请求在未接受时保持，接受后等待完成；错误响应使 LSU 的 `writeback_exception_o` 输出 `EXCEPTION_FAULT_STORE`（内部编码 `6'h17`），并在结果路径给出维护请求地址。新测试检查三种操作各自的背压、成功、错误和排空行为；cache 写回组件测试另检查维护失败与恢复。这些检查限于 LSU/Cache 输出，不能写成 CPU 已设置 mcause=7 或已精确陷入。维护 CSRRW 走 CSR/WB 路径；流水控制仅在 LOAD/STORE 标记且 LSU 完成时采纳内存异常，维护 CSR 已走 WB 后的 LSU 错误不一定形成 CPU 精确异常。本次地址迁移未改变这一既有机制，也未完成维护错误的 CPU 精确陷入验证。

**P0-2 已修正。** 非委托机器中断按 `MEI > MSI > MTI` 选择。公开 CSR 端口写入 MIP/MIE/MSTATUS，覆盖三个 pending 位的全部 8 种组合；还验证了真实外部中断输入和 `0x7C0` timer 到期。

未实现地址的 CSR 访问报非法指令，包括零源的 CSRRS/CSRRC、立即数零源访问及未知的只读编码地址。已实现只读地址允许不写入的读取；CSRRW/CSRRWI 总是构成写尝试，CSRRS/CSRRC 的 rs1 非 x0（即使寄存器数值为 0）或立即数非零也构成写尝试，均报非法指令。固定字段与只读地址分别处理：MISA 位于读写地址区，对其写入合法但固定值不变。本次定向测试使用 MULDIV=1，MISA 为 `0x40001100`。

`mvendorid/marchid/mimpid`（`0xF11–0xF13`）现在显式实现为只读零；这三个标准标识寄存器必须可读，规范允许返回零。它们不再依赖未知地址的默认分支。SUPPORT_SUPER=0 时未实现的 S-mode CSR 与 delegation CSR 也判非法；参数为 1 时保留原实现。对非法操作，CSR 结果写使能撤销，非法指令编码保留在异常值路径。

## 仿真与二进制兼容

新固件必须与新位流配套。旧固件使用的 `0x3A0–0x3A2` 在新硬件上会陷入非法指令；新地址固件也不能用于旧位流。没有把旧证据的来源哈希替换为新源码哈希。

历史测试平台使用 `0x7B2/0x8B2` 传送打印/退出命令。生产编译下这两个地址未实现；`verilog_sim`/`verilator` 保留原内建仿真处理。新增 `TRIHA_SIM_CTRL_EXTERNAL` 仅用于现有 Windows 仿真运行器，使地址合法、由外部 TB 检查退出码并结束仿真，避免内部 `$finish` 抢先跳过测试平台判定。此宏没有加入任何生产 PDS 目标。原 ELF smoke 单/双发射和 GCC runtime 两模式均重新通过。

两树各自修改自身的 `triha_csr.v`、`triha_lsu.v`，未相互覆盖前端或其他数据通路。新增 `triha_csr_regfile.v` 派生自 vendor 原文件并保留 Apache-2.0 许可；两树的 vendor 核/Cache 共 35 个清单文件逐一哈希验证通过。CPU 树的 smoke filelist 同时保留 vendor regfile，供旧核对照实例使用；当前 TriHa 实例明确连接维护派生模块。

## FENCE.I / Zifencei

官方下载件说明 FENCE.I 已从强制基本 I 指令集移出，属于 Zifencei。实际 Windows GCC 15.2.0 对仅含 `fence.i; ret` 的汇编探针执行：

```text
riscv-none-elf-gcc -march=rv32im_zicsr -mabi=ilp32 -c fence_i.S
    非零退出：fence.i requires zifencei
riscv-none-elf-gcc -march=rv32im_zicsr_zifencei -mabi=ilp32 -c fence_i.S
    PASS
riscv-none-elf-readelf -A rv32im_zicsr_zifencei.o
    Tag_RISCV_arch: rv32i2p1_m2p0_zicsr2p0_zifencei2p0_zmmul1p0
```

实际完整路径、参数和输出记录在 `document-zifencei-20261102T161858914012Z/result.json`。两树现有 cache runtime 编译入口已声明 `_zifencei`，其自修改代码/FENCE.I 检查通过。建议正文称“RV32I 基础 ISA，按配置支持 M、Zicsr 与 Zifencei”；包含 FENCE.I 的软件配置写 `rv32im_zicsr_zifencei`。通用 `performance_march=rv32im_zicsr` 仅覆盖其实际编译程序，不可据此把 FENCE.I 归入基本 I；本任务没有更改历史 CoreMark 工具链声明或测量值。
